> `JTAG-DP STICKY ERROR` 是**果**，不是**因**。它只是说「JTAG 调试口读到了一个粘滞错误位」，而这个位的常见来源是目标侧复位/时钟被抽掉。

## 三、排查过程

按"先排除，再定位"推进，每一步都留判据，不靠猜。

### 阶段 1：排除 PS 软件层

| 怀疑对象 | 验证方法 | 结论 |
|---|---|---|
| `Fclk_Init()` 本身写错 | 与两份**已出图存档**的 `Fclk_Init()` 逐行 diff，完全相同 | ❌ 排除 |
| PS 访问了不存在的地址（死地址 0x80000000/0x80100000） | 全程零访问记录 | ❌ 排除 |
| PS GPIO / UART / CRG 配置 | 与 `MainProject` 已跑通的图像版本一致 | ❌ 排除 |
| `Processor_System_Reset_0` 实例本身 | 其 5 个输出本来就全空接；官方也是空接，官方用 `Constant_1` 补 `pll_locked` | ❌ 排除（非致命，但埋下了 HP0 时序问题的伏笔） |

### 阶段 2：排除 FD 侧 FCLK 分频

| 怀疑对象 | 验证方法 | 结论 |
|---|---|---|
| FD 侧把 p2f_clk 配错了 | `soc_plat.c:1397` `div_fclk0 = 0x00000001` → **÷2**；`soc_plat.c:1402` `div_fclk1 = 0x00000007` → **÷8**；`platform/Design.xml` 里 `IO_400_Actual = 399.96 MHz` ⇒ **199.98 / 49.995 MHz**，与 PL 侧 PLL 分频 2/8 **完全一致** | ❌ 排除 |

### 阶段 3：锁定根因 A —— 时钟域

方法：把 DI 里每条时钟网的实际成员列出来比对。

| 时钟网 | 修复前成员 | 判定 |
|---|---|---|
| `p2f_clk0`（199.98 MHz） | `slave_hp0_axi_aclk`、`uiFDMA_0.M_AXI_ACLK`、`Processor_System_Reset_0.clk` | 图像/HP0 域 |
| `p2f_clk1`（49.995 MHz） | `AXI_Matrix_0.aclk`、`AXI_GPIO_0/1.s_axi_aclk`、`AXI_Protocol_Converter_0/1/2.aclk`、`axi_lite_pwm_0.s_axi_aclk` | AXI 从端域 |
| **`master_gp0_axi_aclk`** | **在 `p2f_clk0`（199.98 MHz）** | ❌ **跨域！** |

**机理**：AXI 的 AR/AW 握手通道没有跨时钟域同步器。主口在 200 MHz、从端在 50 MHz，事务发出去后握手永远等不到应答 → **总线挂死** → PS 卡在一条 `load` 指令上 → 看门狗/异常触发复位。

### 阶段 4：锁定根因 B —— AXI ID 位宽

DI 里 `AXI_Matrix_0` 的六个参数全是错的：

| 参数 | 修复前（错） | 应为 | 依据 |
|---|---|---|---|
| `AL_AXI_ID_WIDTH` | **2** | **13** | = USER + 1 |
| `AL_AXI_ID_WIDTH_USER` | **1** | **12** | PS GP0 的 ID 是 12 bit |
| `AL_CONNECTIVITY_MODE` | **1**（SAMD） | **0**（SASD） | 共享数据模式 |
| `conectivity_type` | Multi-Data(SAMD) | **Shared-Data(SASD)** | 同上 |
| `AL_US_AXI_THREAD_ID_WIDTH` | `0x01` | `0x0000000C` | SASD 下需区分线程 |
| `us0_thread_id_width` | **1** | **12** | 同上 |

**机理**：PS 发出 12 bit ID，被矩阵截成 **1 bit** → 多个不同事务撞到同一个 ID → 应答张冠李戴 → 总线挂死。与根因 A **叠加**。

### 阶段 5：锁定根因 C —— 协议转换器空接

| 检查项 | 结果 |
|---|---|
| `AXI_Protocol_Converter_0` 的 `DS_AXI` | **完全空接**（对应死地址 `0x80000000`） |
| `AXI_Protocol_Converter_1` 的 `DS_AXI` | **完全空接**（对应死地址 `0x80100000`） |
| `system.violation` 中 `S_AXI_Lite` 未连接告警 | **20 条** |

**机理**：PS 一旦访问 `0x80000000` / `0x80100000`，转换器下游什么都没接 —— 事务又从另一条路径挂死。

## 四、根因（三条叠加，缺一不可）

### 4.1 根因 A：GP0 主口与整条 AXI 链跨时钟域（决定性）

`master_gp0_axi_aclk` 挂在 `p2f_clk0`（199.98 MHz），而矩阵 / 三个转换器 / 两个 AXI GPIO / PWM 全挂在 `p2f_clk1`（49.995 MHz）。

> **硬约束：PS 的 GP0 主口时钟必须与 AXI 全链路（矩阵、协议转换器、所有从端 `s_axi_aclk`）同域。**
> 官方 11 个含 GP0 主口的工程，无一例外。

### 4.2 根因 B：AXI ID 被截成 1 bit

矩阵 `AL_AXI_ID_WIDTH=2 / AL_AXI_ID_WIDTH_USER=1`，把 PS 的 12 bit ID 压成 1 bit，事务 ID 撞车。

### 4.3 根因 C：两个协议转换器下游空接

`Converter_0/1` 的 `DS_AXI` 未连到 `AXI_GPIO_0/1`，形成两个死地址窗口。

### 4.4 为什么表现成"一启动就复位"而不是"读不到数据"

三条叠加后，**第一笔 AXI 事务就大概率挂死**。PS 启动早期第一阶段动作就是访问 AXI 外设（读 VERSION / 写 PWM），于是：

```
PS 启动 → 发第一笔 AXI 事务 → 握手无应答（跨域 + ID 撞车）→ 总线挂死
       → CPU 卡在 load 指令 → 异常/看门狗复位 → JTAG 侧读到一个粘滞错误位
       → 报 JTAG-DP STICKY ERROR（与真实病因毫无关系）
```

## 五、解法（可照做）

### 5.1 时钟归域：把 GP0 主口迁到 `p2f_clk1`

在 DI 里把 `master_gp0_axi_aclk` 从 `p2f_clk0` 网移除、加入 `p2f_clk1` 网。修复后拓扑：

| 时钟网 | 频率 | 成员 |
|---|---|---|
| `p2f_clk0` | 199.98 MHz | `slave_hp0_axi_aclk`、`uiFDMA_0.M_AXI_ACLK`、`Processor_System_Reset_0.clk`（**仅图像/HP0**） |
| `p2f_clk1` | 49.995 MHz | **`master_gp0_axi_aclk` ★**、`AXI_Matrix_0.aclk`、`AXI_GPIO_0/1.s_axi_aclk`、`AXI_Protocol_Converter_0/1/2.aclk`、`axi_lite_pwm_0.s_axi_aclk` |

> **方向选择的判据**：为什么是"把主口迁到 50 MHz"，而不是"把 AXI 链迁到 200 MHz"？
> ① `p2f_clk0` 本来就有既有 hold 违例（HWNS −2.322 ns），搬上去会恶化；
> ② PS 侧 PWM 频率公式常量 `49995000.0` 已按 50 MHz 写好，迁 AXI 链要改 3 处软件。

验证：`hdl/system.v:1142`

```verilog
assign w_port__ARM_Processor_System_0__master_gp0_axi_aclk = w_net__ARM_Processor_System_0__p2f_clk1 ;
```

### 5.2 矩阵六参数改回 SASD / 13 / 12

```
AL_AXI_ID_WIDTH          = 13
AL_AXI_ID_WIDTH_USER     = 12
AL_CONNECTIVITY_MODE     = 0            (Shared-Data SASD)
conectivity_type         = Shared-Data(SASD)
AL_US_AXI_THREAD_ID_WIDTH= 32'h0000000C
us0_thread_id_width      = 12
```

> ⚠️ **必须走 GUI**：双击 `AXI_Matrix_0` → 改 `AXI ID WIDTH = 12` / `Connectivity Mode = Shared-Data(SASD)` → 点 **Apply/OK** → 再 `Generate design`。直接改文件**不会**触发 IP 重生成（详见第六节）。

### 5.3 补 34 条信号级接线

从官方 `14_axi_gpio_pl_intr` 的 DI 原样移植：

- `AXI_Protocol_Converter_0 ↔ AXI_GPIO_0`：**17 条** `adHocConnection`
- `AXI_Protocol_Converter_1 ↔ AXI_GPIO_1`：**17 条** `adHocConnection`
- 另加 2 条总线级 `interconnection`（`Converter_*.DS_AXI → AXI_GPIO_*.S_AXI_Lite`）
- 两个 `AXI_GPIO_0/1` 的 `AL_AXIS_ADDR_WD` 由 9 改为 **32**

效果：`system.violation` 的 warn 从 **40 → 6**。

### 5.4 最终验收判据（实测）

| 路径组 | SWNS | 违例 | HWNS | 违例 |
|---|---|---|---|---|
| `p2f_clk1 → p2f_clk1`（50 MHz AXI 域） | **13.013 ns** | **0** | **0.041 ns** | **0** |
| `p2f_clk1 → GEN_PL_GP0S`（GP0 主口发出） | **14.691 ns** | **0** | 0.227 ns | 0 |
| `GEN_PL_GP0S → p2f_clk1`（应答回 PS） | **13.714 ns** | **0** | 0.744 ns | 0 |

> **双向跨时钟域零违例** —— 根因 A 被时序报告**独立证实**修复。

其余实测：综合 9m36s ｜ 位流 `soc_prj.bit` 4.05 MB ｜ `axi_lite_pwm_0` 442 LUT / 192 FF，`u_pwm0/1/2` 各 81 LUT / 64 FF（未被优化掉）｜ 地址解码三方一致：DS0 `0x80000000`→GPIO_0、DS1 `0x80100000`→GPIO_1、DS2 `0x80200000`→PWM，窗口 `0x0C`=4 KB。

## 六、DI 参数三副本机制（本轮返工三次的根源）

### 6.1 四个文件谁说了算

| 文件 | 角色 | 谁读它 |
|---|---|---|
| `system/Design.xml` | **GUI 显示用快照** —— 改它会被 generate 覆盖 | DI 画布 |
| **`ip/<inst>/.params_<inst>.txt`** | **IP 生成器真值源**<br>格式 `名称 : 值 : 类型(U/G) : En/Dis : 下限 : 上限`，`U`=用户可改、`G`=由 U 推导 | IP 生成器 |
| `ip/<inst>/.m_params_<inst>.txt` | 生成器输入快照，三列 `名称; 显示宽度; 值` | IP 生成器 |
| `ip/<inst>/Design.xml` | IP 实例自身参数记录 | 打包/重生成 |

### 6.2 三次返工的真实原因

| 第几次 | 做法 | 结果 |
|---|---|---|
| 第 1 次 | 只改主 DI `system/Design.xml` | ❌ generate 后被 TD **原样回退**成旧值 |
| 第 2 次 | 四处同步改（含 `.params` 真值源） | ❌ wrapper 里仍是 `.AL_AXI_ID_WIDTH(2)`，wrapper 时间戳始终 14:39:59 |
| 第 3 次 | **GUI 打开 IP 参数面板 → Apply** | ✅ 一次成功 |

**关键机制**：改文件**不会**把 IP 标记为 dirty。TD 的 `Generate design` 只重生成互联 RTL（`hdl/system.v`），**不重生成已有 IP 的 wrapper**。必须在 GUI 里 Apply 一次才会重新生成。

**旁证**：矩阵核心 RTL 的文件名带参数 hash ——
`axi_matrix_wrapper_f41f427955dd.v`（旧参数） → `axi_matrix_wrapper_system_AXI_Matrix_0.v`（Apply 后重生成）。
**看这个名字换没换，就知道 IP 到底重生成没有。**

### 6.3 另外三个工具层陷阱

| 陷阱 | 具体表现 | 正确做法 |
|---|---|---|
| **行尾** | `.params` / `.m_params` / IP `Design.xml` 是 **CRLF**；主 DI `system/Design.xml` 是 **LF** | Python 必须用 `open(f,'rb')` / `open(f,'wb')` 二进制模式，文本模式会把 CRLF 静默压成 LF |
| **XML namespace** | MainProject 用 `http://www.accellera.org/XMLSchema/IPXACT/1685-2014`，官方用字面量 `http` | 解析器按 `local-name` 去命名空间后匹配，**不要硬编码 namespace** |
| **接线的权威来源** | `interconnections` 只是 GUI 汇总视图 | **`adHocConnections`（信号级）才是权威**，补接线必须补信号级，端口名要与对端一致 |

### 6.4 为什么没走命令行

| 尝试 | 结果 |
|---|---|
| `design_integrator.exe` | 纯 Qt GUI，**无任何 CLI 选项** |
| `td_commands_prompt.exe` | 是 tcl shell，有 `open_project` / `launch_runs` / `wait_run`，但**没有 DI generate 命令** |
| 结论 | DI 参数修改只能走 GUI |

## 九、如何避免（下次的检查清单）

### 9.1 加 AXI 外设到已有图像工程时，按顺序过这七关

1. **时钟域**：DI 里核对 `master_gp0_axi_aclk` == `AXI_Matrix_0.aclk` == 所有 `Converter_*.aclk` == 所有从端 `s_axi_aclk`，**必须是同一根网**。不确定就抄官方 `14_axi_gpio_pl_intr`。
2. **矩阵 ID 参数**：`13 / 12 / 0(SASD) / 0x0C / 12 / Shared-Data(SASD)`，逐项对官方。
3. **转换器下游**：每个 `Converter_*.DS_AXI` 都必须有连线；`violation` 里 `S_AXI_Lite` 未连接告警应为 **0**。
4. **改 IP 参数一律走 GUI Apply**，然后核三件事：① wrapper 里参数值变了；② 核心 RTL **文件名 hash 换名了**；③ violation error 数变了。
5. **综合前跑一次 generate**，把 `error` / `warn` 数与官方同型工程对照 —— 只关心"我比官方多了什么"。
6. **看时序先看目标域**：本次是 AXI 域（50 MHz）必须全绿；同时确认既有违例**没恶化**（比端点数和 ns 值）。
7. **地址三方对齐**：DI `system.address.xml` ↔ 矩阵 per-DS 窗口 ↔ PS 侧 `#define` 基址，必须三个数完全一样。

### 9.2 排障习惯上的三条

1. **`JTAG-DP STICKY ERROR` 不要往 JTAG 信号完整性上找**。先看 `Platfrom initialization Succeed` 之后应用是否开始跑；PS 侧复位优先怀疑总线挂死。
2. **`Download Success!` ≠ 程序跑起来了**。要把"位流下载成功 / Platform 初始化成功 / 应用启动"三段分开判。
3. **PS 一启动就复位，优先怀疑 AXI**，不要先怀疑时钟分频、DDR、看门狗。判据：`Fclk_Init()` 与已出图存档 diff 一致就能排除分频。

### 9.3 一条经验法则

> **凡是"官方例程能跑、我的工程不能跑"，先用 diff 把差异压缩到可枚举的项，再逐项和官方对齐 —— 不要靠推理。**
> 本轮 11 个官方工程扫下来，根因 A 一次就定位了；而在此之前靠推理绕了很久。

## 十、附：同期另一个阻断问题（与 AXI 无关）

修复完成后准备下载时，OpenOCD 报：

```
target arm
Info : Listening on port 5555 for rbb connections
Error: libusb_get_device_list() failed with LIBUSB_ERROR_NO_DEVICE
```

**这是另一个完全独立的问题，不是复位故障**：

| 项 | 结论 |
|---|---|
| 根因 | **FD 自带的 libusb 1.0.23 在本机全局枚举失败**（`libusb_get_device_list()` 恒返回 `-4`） |
| 证据 | 同机换 pip `libusb-package` 的 **1.0.30** 立刻枚举到 9 个设备，目标 `0403:6042` 在 bus=1 addr=6 |
| 修复 | 备份后用 1.0.30 覆盖 `FD\toolchain\openocd\fpsoc\bin\libusb-1.0.dll`（26 个导出符号齐全，ABI 向下兼容） |
| 备份 | `libusb-1.0.dll.bak-1.0.23-20261031` |
| 注意 | **FD 重装/升级会退回 1.0.23 → 故障复现**，再覆盖一次即可 |

详细记录见 `.workbuddy\memory\2026-10-31.md` §二十二。
