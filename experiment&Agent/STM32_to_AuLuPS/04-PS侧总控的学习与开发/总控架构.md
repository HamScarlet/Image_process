**读图口诀**：自上而下是**指挥关系**，不是数据流水线。🟣 紫色 = 人机交互端（人说话的地方）；🟡 橙色 = PS 总控（**只下发与汇聚，不碰像素**）；🟢 绿色 = PL 三条链并行（视觉跑实时、决策跑确定性、执行跑闭环）；⚪ 灰色 = STM32 独立冗余（**不接主控制**）。中间三条竖线是两侧之间全部的通路，其中 I3 目前**是断的**（见第六节）。

一个必须先建立的认知：**这条链上跑的不是一种数据，而是两种完全不同性质的数据**——像素（每秒上亿字节、要求带宽）与指令（每秒几条、要求确定）。把它们放在同一条通路上考虑，是架构上最容易犯的错。

**读图口诀**：上下两块是**两条独立的时间轴**，不是上下游。🟡 橙色慢回路的输出（阈值）是快回路的**输入参数**，两者之间是"设置一次、长期生效"，不是"每帧都通信"。底部红框是三条不可模糊的边界。

| 决策层 | 归属 | 特征 | 典型内容 | 延迟要求 |
|---|---|---|---|---|
| **反应式（reflex）** | **PL** | 快、确定、简单 | 急停、避障、帧内方位判断 | **确定性**（固定时钟数 + ≤1 帧） |
| **规划式（deliberative）** | **PS** | 慢、灵活、复杂 | 模式切换、路径策略、阈值标定、UI 交互 | 不敏感（10–100 ms 级可接受） |

> **为什么指令生成必须放 PL（D1 决策，已定）**：安全关键路径若经 PS 的裸机调度与中断，延迟**不可计算**；而 PL 的并行比较器 + 状态机延迟是**固定时钟数**。安全功能需要的是"延迟可算"，不是"平均很快"。反过来，模式切换、阈值标定这类事"慢 20 ms 也无所谓"，放 PS 才能享受可改程序、可打日志的便利。

**一句话记住分工依据**：**慢的事交给"能改代码"的（PS），确定性的事交给"延迟可算"的（PL）。**

## 四、逐层详解（4 层）

### 第 1 层：串口屏 TJC（人机交互端）

| 项目 | 内容 |
|---|---|
| 选型 | 陶晶驰 **TJC 系列**（D4 决策，已定），1024×600 面板，与 HDMI 外接面板同规格 |
| 通道 | 接 **PS 的 UART**，契约 **I6**（TJC 指令集） |
| 输入 | 触摸事件、按钮触发（`b0`–`b3` 模式切换 / 急停 / 参数进入 / 蓝牙配对） |
| 输出 | 数值控件 `n0`–`n3`（距离等级 / 障碍方位 / 速度 / 里程，≥10 Hz）、文本 `t0`–`t2`（模式 / 路面特征 / 告警，事件驱动）、波形组件（编码器反馈，≥5 Hz） |
| 干什么 | 把机器内部状态变成人能看的数字，把人的意图变成 PS 能读的串口帧 |
| **为什么走 PS 而不是 PL** | ① PL 的 IO 已被 MIPI / HDMI / 电机 / 编码器 / 超声波占满（硬约束 C4：BANK33 拥挤）；② 屏的内容本质是"状态与模式"，属于总控职责；③ TJC 指令集是**字符串协议**，PL 做字符串解析会吃掉大量 LUT，而 PS 上只是几行 C |
| 为什么刷新率只有 10 Hz | 屏走串口，115200 bps 下一帧文本指令约几十字节；且"人眼看数字"这个需求本身就只需要 10 Hz。**刻意做成慢回路** |

> ⚠️ **待确认（不编造）**：屏接 **PS 的哪一路 UART** 尚未定。现有配置只使能了 `UART1PS`（`soc_plat.h`，`UART0PS_ENABLE` 为注释状态），而 UART1（`0xF8401000`）已被日志占用。三条候选：① 复用 UART1、日志改到屏上显示；② 打开 `UART0PS`；③ 接 PL 侧 UART（J16/K16）由 PL 转发。**须在阶段 7 冻结前定案**，因为 I6 契约要求"波特率、帧结构、控件变量地址映射"三项齐备。

### 第 2 层：PS 总控（决策端）

| 项目 | 内容 |
|---|---|
| 参数 | 双核 Cortex-A35（本平台只用 Core0）· 裸机 standalone · EL3 · **CPU 999.9 MHz**（33.33 MHz × 120 ÷ 2 ÷ 2） |
| 输入 | I6（屏触摸）· I7（蓝牙）· **I3 状态回读**（当前无通路，见第六节） |
| 输出 | **I3 阈值 / 模式下发**（当前无通路）· 屏显示数据 · 日志（UART1 `0xF8401000` @115200） |
| 干什么 | 模式管理、阈值计算、状态汇聚、异常恢复、UI 与日志 |
| **为什么 PS 当总控** | ① 它是全系统唯一"改一行代码就能改行为"的核——PL 改一次要重新综合 + 布线；② 它本来就在启动链上（BootROM → FSBL → 应用），天然掌握全局与启动时序；③ 它处理的是"策略级"而非"像素级"数据，算力与延迟双重富余 |
| **为什么"不碰像素"（红线①）** | 1080p60 的像素流量 ≈ **497 MB/s**，而 PS 的取指、栈、`printf` 同样要走 DDR。DDR3-1333 × 32 bit 峰值 ≈ **5.33 GB/s**，平均带宽够，但 PL 一发起长突发，CPU 就会遇到延迟尖峰。**参与像素搬运 = 与 PL 抢带宽**，是分工而非竞争 |
| 落点 | 总控代码**全部落在 `fdma_en` 应用层**，② ③ ④ 层不动（见下图） |

**读图口诀**：从上到下是**编译依赖方向**（上层用下层的接口，下层不知道上层存在）。四层同色表示它们同属 PS 一套软件栈；总控的新增模块只出现在 ① 层，② ③ ④ 保持原样——这条决定了改造的"爆炸半径"：**PS 侧只动一个应用工程**。

> **为什么这个落点很重要**：② ③ ④ 三层的文件（`soc_plat.h`、7 张操作码配置表、`Design.xml`）**全是 hpfTool 从 TD/HPF 自动生成的产物**。一旦在生成物里手改，下次导出即被覆盖。把总控逻辑全部收进 ① 层，就避开了这个陷阱。

### 第 3 层：PL 执行（眼睛与手脚）

| 项目 | 内容 |
|---|---|
| 参数 | 52,480 LUT6 / 104,960 DFF / 240 DSP / 8 PLL · PL 参考时钟 **p2f_clk0 199.98 MHz**（1999.8 ÷ 10） |
| 三条链 | **视觉链**（I1 → I2）：MIPI CS500 → 软 D-PHY → ISP → 图像算法 → NPU → 框选/标注/像素 LOGO → HDMI<br>**决策链**（I8）：超声波多路 TOF + 视觉目标框方位 → 硬件并行比较 → 状态机 → 前行/转向/制动<br>**执行链**（I4/I5）：编码电机闭环 → PID → PWM → 紧急制动 |
| 输入 | I1（摄像头）· I8（超声波）· I5（编码器）· I3（PS 下发的阈值/模式） |
| 输出 | HDMI（视觉呈现）· I4（PWM + 方向 + 使能）· I3（状态与视觉摘要上报） |
| 干什么 | 实时显示、反应式判决、闭环执行——**全部要求延迟可算** |
| **为什么反应式落 PL** | 三条链并行是硬件天生能力：比较器、状态机、PWM 生成**各占一块逻辑、互不排队**。同样的活放在 PS 上，串口屏解析、蓝牙、日志会随时打断，延迟从"固定 N 拍"退化成"看运气" |
| **为什么不能自建帧缓存（C5）** | PL 的 IO 是 **HRE，不支持外挂 DDR3** ⇒ 帧缓存只能走 PS 侧 1 GB DDR3，经 FDMA 读写。这就是视觉链与 PS 之间存在物理耦合的原因 |
| **阈值为什么不能自改（红线②）** | 若 PL 能自行调整判据阈值，"谁在做决策"就说不清了——总控名存实亡，且行为无法从 PS 侧复现与追溯 |

### 第 4 层：STM32（安全带）

| 项目 | 内容 |
|---|---|
| 定位 | **传感器协处理 + 安全冗余**（D5 决策，已定），**不参与主控制** |
| 通道 | **I9**（与 PS/PL 的 UART，含冗余数据与兜底指令）· **I10**（对 IMU / 红外 / 独立超声波） |
| 干什么 | 采集 IMU / 红外 / 独立超声波；**通信超时后自主兜底制动**；紧急制动执行（冗余） |
| **为什么必须保留** | 冗余假设：若 PS/PL 失效，STM32 靠"心跳超时"自行制动。这是**唯一不依赖 DR1 的**安全手段——因为 DR1 侧当前自恢复能力为零：WDT 未启用、无中断、无健康寄存器（详见 `总控平台建立起的问题.md`） |
| 与主动链的关系 | 正常运行时它只"看和报"；只在超时/故障时才"动手"。**两条路径共享的执行机构是电机**，因此 I4 的"失效安全默认态"（使能位默认 = 0）是这条冗余链能否成立的关键 |

## 五、节拍所有权与时钟域

架构能不能成立，看的是**每一层的节拍由谁定**。

| 节拍 / 域 | 值 | 谁决定 | 谁必须服从 | 出处 |
|---|---|---|---|---|
| 摄像头像素节拍 | `S_hs_rx_clk` | **CS500 自身配置** | PL 视觉链 | `system.v` |
| 显示像素节拍 | `pclkx1`（1024×600） | **HDMI / 屏标准** | PL 输出链，**不可漂移** | `pll` clk0 |
| PL 参考时钟 | **p2f_clk0 199.98 MHz** | PS PLL（1999.8 ÷ 10） | PL 的 FDMA 地址生成 | `Design.xml` |
| PS 核节拍 | **999.9 MHz** | PS PLL（33.33 × 120 ÷ 2 ÷ 2） | PS 全部软件 | `soc_plat.h` |
| 串口屏节拍 | UART 波特率（待定） | PS UART 分频 | 屏；**慢回路，帧率极低** | I6 契约 |
| 反应式判决节拍 | 固定周期（待定） | PL 计数器 | 电机闭环 | I8 契约 |

**为什么不能合成一个钟**：四方诉求互相冲突——摄像头希望越快越好，HDMI 必须精确符合标准（差一点屏就点不亮），PS 的核需要高主频，而串口屏只有 115200 级。硬凑成一个钟，要么显不亮、要么花屏、要么屏刷不动。

> **本节最值得记住的一句**：**慢回路（屏/蓝牙/模式）与快回路（判决/执行）必须由不同节拍驱动**——这正是"PS 总控 + PL 执行"分工的物理根因，不是风格偏好。

> ⚠️ **这是本架构最大的硬缺口**：规划 v2.0 把 I3 定义为"AXI（FDMA / AXI-ERAM / AXI-GPIO / PL 中断）+ 控制 / 状态 / 阈值 / 屏显数据四类寄存器分区"，但基线平台的 `Design.xml` 里 **GP0/GP1 主从四个方向全为 0、全部 P2F 中断使能位为 0**。也就是说：**"PS 下发阈值"这件事，在当前硬件上做不到。** 阶段 7 的 I3 契约必须先完成下面的改造才能冻结。

### 两条改造路线

| 路线 | 做法 | 前置条件 | 延迟量级 | 代价 |
|---|---|---|---|---|
| **A · 正统** | PL 侧 Design Integrator 增开 **Master_AXI_GP0**（PS 主 → PL 从），挂 AXI-ERAM / AXI-GPIO；同时开 **F2P 中断** | 需要 PL 侧 IP 可用（**待确认**：本平台 `pl_driver` 目录为空，规则文件列了 10 个 PL IP 驱动但一个都没用到） | 寄存器读写 ≈ 百纳秒级；中断响应 ≈ µs 级 | PL 需重新综合布线，PL 侧改动风险高 |
| **B · 低成本起步** | 复用**已有**的 HP0 64 bit 通道：PL 把状态写进 DDR 控制块，PS 轮询读取 | 无需改 PL 现有通路 | 由轮询周期决定（如 10 ms） | PS 读前须处理**缓存一致性**（DDR 全段为 `NORM_CACHE`）：把该区划进 `.noncacheable`，或读前 `AlCache_FlushDcacheRange` |

> **建议：先 B 后 A。** 理由：B 不动 PL 现有通路（PL 综合一次的时间与风险都高），能在"总控"阶段先把"**状态可见**"跑通，让 PS 侧的模式机与屏显逻辑先落地可测；等"阈值下发"变成真需求时再上 A——而那时 PL 本来就要因为图像算法或 OSD 改动而重综合，一起改最省。

### 控制链推进顺序（谁先谁后、靠什么推）

1. 上电 → CSU BootROM 读启动模式（`0xF8800200`）→ 加载 FSBL 到 OCM → 验签 → 释放 Core0；
2. FSBL Stage 1：`Soc_PlatInit()` 7 张配置表（**先钟后外设**）+ `fd_ddr_init()`；
3. FSBL Stage 2：读盘 + 校验（JTAG 模式直跳 Stage 4）；
4. FSBL Stage 3：逐个 Partition 加载（P1 = PL 码流）；
5. FSBL Stage 4：`AlFsbl_Handoff()` 跳转到应用（**不返回**）；
6. 应用：延时 → banner → `Fclk_Init()` 释放 PL 复位（`0xF8806330` 置 `0xF0`）→ **总控接管**；
7. 总控接管后：读 FSBL 状态（`0xF8806184`）→ 初始化屏与蓝牙 → 建立状态汇聚回路 → 等 I3 通路可用后开始下发阈值。

## 七、其他细节速查

| 项 | 出处 | 说明 |
|---|---|---|
| **同一寄存器被四处操作** | `ps_pl_0` 表 · `AlTop_GPPortEnable()` · `Soc_PsPlInit()` · `Fclk_Init()` | `0xF8800080` / `0xF8801078` / `0xF8806330` 三个寄存器被四处反复读写，改硬件时极易漏改 |
| **应用绕过了 HAL** | `main.c` 的 `Fclk_Init()` | 平台本有正式接口 `AlTop_P2F_RstAssert / Release()`，应用却用裸地址魔数手工实现 |
| 日志口 | `0xF8401000`（UART1）@115200 | 走 Type-C 那个口（PS MIO48/49）；接错口会一行日志都没有 |
| 应用里没有 FDMA 代码 | 全仓 grep | 平台名里的 `fdma_en` 指 **PL 侧 FDMA 通道被使能**，PS 侧只提供通路（HP0 + DDR） |
| 打印环形缓冲 | `__async_print_ring_buf_size` | 1 MB，位于数据段内 |
| 栈 / heap | 链接脚本 | 应用栈 6 MB、FSBL 栈 8 KB；**两者默认值不同，别混用** |
| `.rt_text` 搬运段 | map | LMA `0x08011780` → VMA `0x61000000`（把热代码搬进 OCM 执行的老手法） |
| 看门狗 | 两处独立证据 | `AlFsbl_InitWdt()` 被注释 + `WDTPS_ENABLE` 注释 ⇒ **WDT 未启用，卡死无人复位** |
| FSBL 余量 | `fsbl.bin` = 207,488 B vs OCM 252 KB | 余量约 **44 KB**，再加功能要留意链接失败 |
| 双开关陷阱 | `soc_plat.h` | `*PS_ENABLE`（外设是否被配置）与 `HAVE_*_DRIVER`（驱动是否编进来）是两回事；实测 `HAVE_IICPS_DRIVER` 已定义但 `I2C0PS / I2C1PS_ENABLE` 均为注释 |

**故障对照表（现象 → 首先怀疑什么）**：

| 现象 | 首先怀疑 |
|---|---|
| 串口一行都没有 | 接错口（**必须 UART1 = Type-C**）；或 FSBL 没起来（启动模式 / SD 镜像分区顺序） |
| 串口日志**反复重来** | 启动回滚成环（`MULTI_BOOT` 递增 + 软复位），检查 SD 镜像分区顺序 |
| 有 banner、HDMI 全黑 | 先看 `[RESULT] p2f_rst_n[3:0]` 是否 `F`；是 `F` 则问题在 PL 侧（PLL / fifowait / VTC） |
| **偶发**花屏 / 黑屏 / 死机 | DDR 训练边际性（`fd_ddr_init()` 返回值被丢弃，失败不会上报）；查 `[DDR INFO]` 是否稳定 |
| 屏上数字不刷新 | I6 通路未定（哪一路 UART）；或 PS 侧没有状态来源（I3 未打通） |
| 想用 PS 读 PL 寄存器 | **当前做不到**（GP0/GP1 未使能），只能走第六节的路线 A 或 B |
| 改了硬件但 PS 行为没变 | 忘了重新导出 HPF 并重编（`soc_plat.h` 与 7 张配置表都是生成物） |

## 八、参数一览

### 8.1 接口契约 I1–I10（规划 v2.0 §1.5，冻结后修改须走 CR 单）

| ID | 接口 | 两端 | 物理层 / 协议 | 冻结阶段 |
|---|---|---|---|---|
| **I1** | 摄像头输入 | CS500 → PL | MIPI CSI-2，**2 lane，RAW10**（PL 软 D-PHY） | 阶段 2 |
| **I2** | PL 内部视频流 | ISP / 算法 / NPU / OSD 之间 | 并行视频（行场同步）或 AXI-Stream | 阶段 2 |
| **I3** | PL ↔ PS | PL ←→ A35 | AXI（FDMA / AXI-ERAM / AXI-GPIO / PL 中断） | 阶段 7 |
| **I4** | PL → 电机驱动 | PL → 驱动板 | PWM + 方向 GPIO + 使能 | 阶段 6 |
| **I5** | PL ← 编码器 | 编码电机 → PL | 正交增量（A/B/Z）或霍尔 | 阶段 6 |
| **I6** | PS ↔ 串口屏 | PS ←→ TJC | UART（TJC 指令集） | 阶段 7 |
| **I7** | PS ↔ 蓝牙 | PS ←→ 手机 / 上位机 | USB 蓝牙适配器或串口蓝牙模块 | 阶段 7 |
| **I8** | PL ↔ 超声波 | 超声波模块 → PL | 触发 / 回波（GPIO + 计时）或多路 TOF | 阶段 5 |
| **I9** | PL/PS ↔ STM32 | STM32 ←→ PS/PL | UART | 阶段 8 |
| **I10** | STM32 ↔ 传感器 | STM32 ←→ IMU / 红外 | I2C / UART / ADC | 阶段 8 |

其中 **I4 / I5 / I6 / I8 为本架构新增**，须重点评审。

**I4 电机控制帧字段（PL 内部寄存器 + 驱动输出）**

| 字段 | 位宽 | 说明 |
|---|---|---|
| 目标速度 L/R | 16+16 bit | 左右轮目标速度（编码器计数/秒） |
| PWM L/R | 12+12 bit | 实际输出占空比（PID 输出） |
| 方向 L/R | 1+1 bit | 正 / 反转 |
| 使能 | 1 bit | 驱动使能（**失效安全默认 = 0**） |
| 制动等级 | 2 bit | 0 = 无 · 1 = 预警 · 2 = 减速 · **3 = 紧急制动** |
| 编码器 L/R | 32+32 bit | 累计计数（闭环与里程） |

### 8.2 地址与容量（含推导）

| 区域 | 地址 | 容量 | 推导 / 出处 |
|---|---|---|---|
| BootROM 保留区 | `0x00000000`–`0x000FFFFF` | **1 MB** | BootROM 访问不到，故应用不从 0 起 |
| **应用运行区（DDR）** | `0x08000000` | **16 MB 链接窗** | `LENGTH=0x1000000` = 16,777,216 B；`_start=0x08000000`、`main=0x08001720` |
| **FSBL 运行区（OCM）** | `0x61000000` | **252 KB** | `0x3F000` = 258,048 B（官方写 256 KB）；`fsbl.bin` = 207,488 B |
| NPU RAM | `0x63E00000` | **256 KB** | `npuram` 段（本平台 NPU 配置为 Disable） |
| **帧缓存（PL 写入）** | `0x0A000000` | 一帧 8 MB | 1920 × 1080 × 4 B = 8,294,400 B ≈ 7.91 MB ⇒ `DSIZEBITS = 23`（2²³ = 8 MB） |
| 日志串口 | `0xF8401000` | — | UART1 @115200 |
| PL 复位控制 | `0xF8806330` | bit[7:4] | `p2f_rst_n[3:0]`，置 `0xF0` = 全部释放 |
| FSBL 状态 | `0xF8806184` | — | `SYSCTRL_S_BASEADDR(0xF8806000) + 0x184`；运行中 `0xFFFF`、成功 `0x0` |
| 启动模式 | `0xF8800200` | — | SD = 0x5 · QSPI32 = 0x3 · JTAG = 0x0 |

### 8.3 关键速率（含推导）

| 量 | 值 | 推导 |
|---|---|---|
| PL 像素带宽需求 | **≈ 497 MB/s** | 1920 × 1080 × 4 B × 60 fps |
| DDR3 理论峰值 | **≈ 5.33 GB/s** | 1333 MT/s × 32 bit ÷ 8 = 5.332 GB/s |
| 占比 | **≈ 9.3%** | 497 ÷ 5332 ⇒ 平均带宽够，**风险在突发抢占** |
| HP0 通道位宽 | **64 bit** | `Slave_AXI_HP0_DATA_WIDTH=64`、`wmode_hp0=0` |
| PS 核主频 | **999.9 MHz** | 33.33 × `CPU_FBK_DIV(120)` ÷ `CPU_REF_DIV(2)` ÷ `CPU_OUT_DIV(2)` |
| PL 参考时钟 | **199.98 MHz** | 1999.8 ÷ 10 |

### 8.4 硬约束（规划 v2.0 §1.6，与本架构直接相关项）

| # | 约束 | 对总控架构的影响 |
|---|---|---|
| C3 | HDMI D1（F16/F17）与片上 ADC0 复用 | 用 HDMI 就不能用 ADC0 ⇒ 模拟采集交 STM32 |
| C4 | **BANK33 外设拥挤**（HDMI / 网口 / CAN / RS485 / 音频 / I2C / UART 共 50 IO） | 新增外设优先 **BANK11 排针 / BANK32 FEP** |
| C5 | **PL IO 为 HRE，不支持外挂 DDR3** | 帧缓存只能走 PS 侧 DDR3（FDMA）⇒ 视觉链与 PS 存在物理耦合 |
| C6 | 电平分裂：PS BANK200 = 3V3 / BANK201 = 1V8 | 接串口屏与电机驱动前须查 pinlist |
| C7 | 按键引脚 pinlist（K19/J19）与 `.adc`（K14/J14）不一致 | 以实测为准；AE 相关按键行为需重新确认 |

## 九、总结

1. **分层**：串口屏（人机）→ PS（总控：模式 / 阈值 / 状态汇聚）→ PL（视觉 / 决策 / 执行三链）→ STM32（传感器协处理 + 安全冗余），四层靠 I1–I10 十条契约连接。
2. **切分依据**：按延迟敏感度劈成两半——反应式（确定性、≤1 帧、固定时钟数）归 PL，规划式（10–100 ms 可接受）归 PS。
3. **第一硬缺口**：I3 契约在当前硬件上不成立（GP0/GP1 与全部 P2F 中断未使能），"PS 下发阈值"必须先改造通路；建议**先走"PL 写 DDR + PS 轮询"的低成本路线**，再上 AXI-GP0 + 中断。
4. **关键约束**：DDR 前 1 MB 不可用（应用从 `0x08000000` 起）；PL 不能外挂 DDR3（帧缓存必走 PS DDR3）；串口屏不能与日志争用 UART1。
5. **落点**：所有总控代码收进 `fdma_en` 应用层一层，②③④ 层不动——因为那些文件全是 hpfTool 生成物，手改会被下次导出覆盖。
